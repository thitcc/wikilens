WikiLens Release runbook

Six steps take main from merged code to a versioned installer in someone's hands. The agent preps the release PR and CI builds the installers; every other step is you gating. The step numbers match the ritual in docs/versioning.html, where the strategy (what the segments mean, when a release is worth cutting) lives.

pick→bump PR→merge→tag→CI build→smoke→release
1 Pick the number you

A feature batch since the last release → minor (0.2.0); fixes only → patch (0.1.1). Full segment semantics: the versioning guide.

Before going further: main is green in CI and your working tree is clean; the release PR must contain nothing but the bump.

2 Release PR agent

Ask the agent to “prep the release PR for 0.2.0”. Concretely it runs:

git checkout -b chore/release-0-2-0
npm run bump 0.2.0    rewrites the 3 manifests, refreshes both locks

npm run bump prints an old → new line per file and refuses the classic mistakes: manifests that disagree on the current version, a malformed version, bumping to the version already there. A refresh command that errors out restores the manifests, so a retry starts clean.

Then the verification bundle (type-check, frontend + tooling tests, clippy, Rust tests), one commit, PR opened. The PR summary doubles as draft release notes.

3·4 Merge, then tag the merge commit you

Merge with a merge commit, as always — never squash. Then, from an up-to-date main so the annotated tag lands on that merge commit:

git checkout main
git pull
git tag -a v0.2.0 -m "WikiLens 0.2.0"
git push origin v0.2.0

Tagging mutates main, so it lives on your side of the line, with merging.

5 CI builds, you validate you

The tag push triggers .github/workflows/release.yml: a Windows runner builds the installers with tauri-apps/tauri-action and attaches them to a draft GitHub Release, invisible until you publish it. A tag that doesn't match the manifests fails in seconds; a cold build runs 15–25 min.

When the run goes green, download both installers from the draft:

WikiLens_0.2.0_x64-setup.exe    NSIS; bootstraps WebView2
WikiLens_0.2.0_x64_en-US.msi    WiX/MSI

The smoked bytes are the shipped bytes: validate the downloads, not a local build. npm run tauri build stays the dev/fallback path; artifact paths and packaged-runtime caveats live in .claude/skills/release-build/SKILL.md.

Then the real gate; the version is a promise that it ran:

✓Walk docs/smoke-checklist.md: item 10 runs on the downloaded installer, not the dev build. Tick the boxes as you go; they get pasted into the release notes.
✓Run the live wiki/API suites: cargo test -- --ignored from src-tauri/.
6 Publish the draft you 
gh release edit v0.2.0 --draft=false

First paste the notes over CI's placeholder body: behavior bullets from git log --first-parent v0.1.0..v0.2.0 (the PRs merged since the last release; their titles are already behavior-level) plus the ticked smoke-checklist boxes. The installers are already attached; nothing to upload.

GitHub Releases are the only changelog. There is no CHANGELOG.md.

When it goes sideways
✓ npm run bump refuses or fails. It names the cause; a refresh command that errors out restores the manifests. Fix the environment, re-run, and check git status for a half-refreshed lock.
✓ The release workflow fails. Re-run it from the Actions tab (delete any stray duplicate draft a re-run leaves). If CI itself is broken, the old manual path is the fallback: local npm run tauri build, smoke, gh release upload onto the draft.
✓ Smoke fails after tagging. Delete the unsmoked draft (it was never visible) and the tag stays a tag: fix on main through normal PR flow, then cut the next number. Never move, reuse, or delete a pushed tag.
✓ Skip “Create release from tag”. A published Release claims installers were built and smoked at that commit; v0.1.0 is tag-only for exactly this reason. CI's draft keeps the rule: it stays invisible until you publish it.
