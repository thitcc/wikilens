How the AI answer gets made

A full technical walkthrough of the retrieval-augmented pipeline: from the summon hotkey (Ctrl+` by default) to a streamed, wiki-grounded answer. Every constant, the verbatim system prompt, and the exact request bodies — with file:line citations throughout.

TL;DR

A question is stripped to keywords and run through MediaWiki search; the top 4 pages are fetched sequentially, rendered HTML → plaintext, and each capped at 8,000 chars. Those excerpts are pasted under a strict "answer only from these" system prompt and streamed from the model at max 1024 output tokens. The model's text is never trimmed or post-processed — Rust and the frontend both pass it through verbatim.

Orchestrated end-to-end by run_ask commands.rs:350. Data flow: hotkey → prompt → ask → search → fetch → reduce → prompt → LLM stream → UI.

1 Retrieval — searching the wiki

Yes — we fetch the first four pages. Here's exactly how they're chosen.

Question → keywords

The raw question never hits the search API. preprocess_query wiki/search.rs:24 splits on whitespace, trims non-alphanumeric edges off each token, and drops ~68 conversational stopwords (case-insensitive; original casing kept). If nothing survives, it falls back to the trimmed original — an empty srsearch is never sent.

// "How do I make Abigail like me?"  →  "Abigail"
// "best crops for winter"          →  "crops winter"
// "Where is Krobus?"               →  "Krobus"

The search request

search::search wiki/search.rs:54 issues a single MediaWiki list=search GET. The page ceiling is a named constant:

/// Default number of pages to pull for a question. Kept small to bound tokens.
pub const DEFAULT_SEARCH_LIMIT: u32 = 4;   // wiki/search.rs:7

Titles come back in the wiki's own relevance order and are not re-sorted search.rs:107.

Eager query rewrite + merge

Keyword search alone mis-fires on messy questions — a rambling "that profitable winter thing you sell, i think it's wine" matches tangential pages ("Version History") instead of Wine. So every ask runs two retrievals concurrently commands.rs · futures_util::future::join:

  • Raw keyword search — the preprocessed query (above).
  • LLM query rewrite — a small, fast model turns the original question into wiki search terms ({"queries":["wine","preserves",…]}) llm::rewrite_query. It hits the model provider (a different host), so it overlaps the wiki search rather than adding latency.

The top rewrite candidates are searched, then merge_hits combines everything — consensus (pages found by both) first, then the rewrite's entity hits, then the raw keyword hits, deduped to top 4. This lifts the real page to the front and pushes junk out (that "wine" question now returns Wine · Wine Table · Preserves Jar). Off with WIKILENS_QUERY_REWRITE=0.

The rewrite needs a fast, non-reasoning model

A reasoning model (e.g. DeepSeek v4) "thinks out loud" into a reasoning_content field, leaves content empty, and takes ~13s — useless for this quick task. The picked model drives the rewrite, so pick a fast non-reasoning one in the footer menu; in Default mode set WIKILENS_DEFAULT_REWRITE_MODEL (falls back to the answer model) commands.rs.

Deterministic net (only if the merge is empty)

If raw + rewrite both come up empty, cheap fallbacks fire in turn, each only while still empty (MediaWiki etiquette): the wiki's own searchinfo.suggestion "did you mean"; a harsher simplify_query keyword pass; then a local title index — Jaro-Winkler (≥ 0.92) fuzzy-match of the query against the game's real page titles, fetched once per session via list=allpages and cached in AppState wiki/titles.rs (skipped for long queries; off with WIKILENS_TITLE_INDEX=0). Still empty → a canned "I couldn't find anything…" answer commands.rs. WIKILENS_TRACE_RETRIEVAL logs each round as JSON (the rewrite's candidates on a wikilens.rewrite line) for offline eval scoring commands.rs:trace_retrieval.

2 Fetch & reduce — before any tokens go out

Turning ≤4 titles into bounded plaintext excerpts.

One request per page, sequential

fetch_pages wiki/fetch.rs:41 loops the titles sequentially — MediaWiki etiquette, deliberately never parallelized — issuing one action=parse&prop=text call per page with a per-request timeout:

const PARSE_TIMEOUT: Duration = Duration::from_secs(12);  // wiki/fetch.rs:26

// query params, one page at a time (fetch.rs:82)
action=parse · page=<title> · prop=text · formatversion=2
disableeditsection=1 · disablelimitreport=1 · redirects=1 · format=json

Rendered HTML → plaintext

Each page's rendered HTML is reduced by wiki::html::to_plaintext wiki/html.rs:48, a streaming tag scanner (not a DOM parser):

  • Drops script/style/svg, TOC, navboxes, edit-section links, print/category cruft.
  • Keeps table data as label | value pipe rows, and Fandom infobox fields as Label: Value — structure the raw wikitext can't provide (it's template/Lua-generated server-side).
  • Decodes HTML entities and collapses whitespace, dropping empty/separator-only lines.

The one hard size cap

/// Per-page character cap. Bounds LLM token cost; overflow is marked truncated.
pub const MAX_PAGE_CHARS: usize = 8_000;   // wiki/fetch.rs:21

truncate_text fetch.rs:226 cuts on a char boundary and appends a literal …[truncated] marker.

No combined-corpus cap

The only limits are 4 pages × 8,000 chars, so the wiki context handed to the model is bounded at roughly 32,000 characters worst case. There is no additional trim on the assembled string. (max_tokens is an output cap, not an input one.)

Fallback path

Any page whose parse call errors or times out is collected and retried in a single batched prop=revisions request fetch.rs:133, cleaned by wiki::wikitext::to_plaintext (prose only — tables/templates stripped). Results are then re-ordered back to search-relevance rank. If everything reduces to nothing, a "found pages but couldn't read them" answer is returned commands.rs:423.

3 Assembly — building the prompt

How the excerpts and the question become one user message.

build_user_message llm.rs:262 concatenates each page as a Markdown block, in relevance order, then appends the question on the final line:

## Winter
Cold season.

## Crops
Grow food.

Player question: best winter crops?
Two things worth knowing

Source URLs are not sent to the model. Only each page's title and text go into the prompt; the url is used solely to build the UI's clickable source list afterward.

The model gets the original question (whitespace-trimmed), not the keyword-stripped search query — so it reads the player's full intent commands.rs:395.

4 Send — the request to the model

The grounding guardrail and the two wire protocols.

Verbatim system prompt · llm.rs:23 You are a game-wiki assistant embedded in an in-game overlay. Answer the player's question using ONLY the wiki excerpts provided below. If the excerpts do not contain the answer, say so plainly and suggest what to search instead. Be concise and practical — the player is mid-game. Use short markdown: bold key items, small lists when comparing options. Do not mention that you were given excerpts; just answer. Wiki excerpts follow, each with its page title.

A separate SCREENSHOT_ADDENDUM llm.rs:29 is appended only when the player attaches a screenshot — so every text-only ask sends the byte-identical prompt it always has. Notice there's no "cite your sources" instruction: sources are attached Rust-side from the fetched pages, not parsed out of the answer.

5 Stream, render — and no trimming

How chunks flow back to the panel, byte for byte.

SSE parsing

A single byte-buffered loop llm.rs:97 drains whole lines and classifies each via the SseLine enum llm.rs:35 — Delta / Done / Ignore / Error. It gracefully skips [DONE], SSE comment/keep-alive lines, role-only and null-content chunks, and surfaces a mid-stream error that arrives on an already-200 body. Each text delta is emitted to the frontend on ask://delta and appended to the running answer:

SseLine::Delta(delta) => {
    on_delta(&delta);            // → emit("ask://delta", …)  commands.rs:441
    answer.push_str(&delta);     // raw append, no processing   llm.rs:107
}

Frontend accumulation & render

// App.tsx:233 — pure concatenation, no separator, no normalization
onAskDelta((chunk) => setAnswer((prev) => prev + chunk));

// App.tsx:360 — final result assigned as-is when ask() resolves
setAnswer(result.answer);

The accumulated string is rendered by AnswerView through react-markdown with a single override that forces links to open in the system browser. No rehype-raw is configured, so raw HTML in the model's output is never rendered — safe by default.

Do we trim the AI response? — No, nowhere.

Neither Rust nor the frontend trims, truncates, caps, or post-processes the answer text. Deltas are appended raw llm.rs:107 and returned as-is llm.rs:126; the frontend concatenates verbatim App.tsx:233 and renders untouched. The only caps in the whole path are max_tokens: 1024 (an output-generation cap the provider enforces) and a .trim() on the input question commands.rs:361.

What comes back

run_ask returns AskResult { answer, sources } commands.rs:60,460. sources is built by mapping over the same fetched pages — every retrieved page becomes a { title, url } source, regardless of whether the model actually cited it. On success the attached screenshot (if any) is cleared; any earlier failure keeps it for a retry.
