WikiLens Versioning guide

A version names a validated installer, never a merge. It bumps only in release PRs; daily PR flow never touches it. The baseline is v0.1.0, tagged 2026-08-04.

The full rationale, with the rejected alternatives, lives in the ADR: vault/2026-08-04_release-scoped-semver.md.

What a version means

WikiLens is an app, not a library; nobody depends on its API. The segments still mean something, just app-flavored:

0.1.0
major Breaks your installed world. The upgrade can't read the previous release's app-data (settings.json, keys.json, history.json, wikis.json) without migration. Stays 0 while pre-stable.
minor A feature release. New capability worth installing, the 0.x workhorse: 0.2.0, 0.3.0…
patch Fixes only. 0.1.1 is “0.1.0 but the bug is gone.” Nothing new.

1.0.0  when app-data survives every upgrade as a kept promise and you'd hand the installer to a stranger. No hurry: 0.x is honest.

Where the version lives

Five files carry the number, and only a release PR may touch them:

package.json           the npm manifest
package-lock.json      two spots, refreshed by npm install --package-lock-only
src-tauri/Cargo.toml   the crate version
src-tauri/Cargo.lock   refreshed by cargo check
src-tauri/tauri.conf.json  names the installers: WikiLens_<version>_x64-setup.exe

Between releases they all read the last released version. That's by design; a number that moved on every merge would be a merge counter, and git already counts merges.

A tag is the snapshot

A git tag is a permanent named pointer to one commit. It copies nothing; the commit is the snapshot, and the tag makes it addressable forever:

✓git checkout v0.1.0 reproduces that exact code, years from now.
✓GitHub serves source zip/tar.gz assets for every tag, and git log --first-parent v0.1.0..v0.2.0 lists exactly the PRs merged between two of them.
✓Unlike a branch it never moves, and the annotated form (git tag -a) carries its own message, author, and date.

The tag must land on the merge commit of the release PR, so create it from an up-to-date main checkout.

When to cut a version

A release is an event, not a schedule: version when an installer is about to land in someone's hands, including your own. Merges pile up on main unversioned in between, and zero releases for a month is a valid state.

SituationCut
A batch of features since the last version is worth installing 0.2.0 (minor)
A version you shipped has a bug that needs fixing now, nothing else rides along 0.1.1 (patch)
Upgrading would break existing app-data without migration major; stays 0.x pre-stable, so in practice: migrate instead
The release ritual

“I want a new version” means walking these six steps. The agent preps; you gate.

1 Pick the number. Features landed → minor. Fixes only → patch. you
2 Release PR. Ask the agent to “prep the release PR for 0.2.0”: branch chore/release-0-2-0, one commit from npm run bump 0.2.0 (rewrites all three manifests, refreshes both locks), /check green. The PR summary doubles as draft release notes. agent
3 Merge. Merge commit, as always. you
4 Tag the merge commit. On main, after pulling the merge: git tag -a v0.2.0 -m "WikiLens 0.2.0" then git push origin v0.2.0. Tagging mutates main, so it lives on your side of the line, with merging. you
5 CI builds, you validate. The tag push triggers .github/workflows/release.yml: installers land on a draft GitHub Release. Download them, walk docs/smoke-checklist.md on the downloaded installer, run the live suites (cargo test -- --ignored, from src-tauri/). This is the real gate; the version is a promise that it ran. you
6 Publish the draft. Paste the notes over CI's placeholder (behavior bullets from git log --first-parent vPREV..vNEXT + the ticked checklist boxes), then gh release edit v0.2.0 --draft=false. The installers are already attached. you
House rules
✓ GitHub Releases are the changelog. No CHANGELOG.md: it would be a third hand-maintained copy of the PR titles and a merge-conflict magnet in every release PR.
✓ A tag without the ritual stays a tag. Never press GitHub's “Create release from tag” shortcut, and never publish a Release whose walk didn't run. CI's draft keeps the rule: a draft is invisible until you promote it. v0.1.0 is tag-only for exactly this reason.
✓ Don't bump outside a release PR. Feature and fix PRs never touch the five version files; two open branches that both bump are a guaranteed conflict.
